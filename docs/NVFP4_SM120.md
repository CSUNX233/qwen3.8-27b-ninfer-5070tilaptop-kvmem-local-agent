# NVFP4 prompt attention：5070 Ti Laptop 调度

本分支在 `prompt_nvfp4_sm120.cuh` 提供单独的 Windows / SM120 调度，保留兼容内核。
只在设备能力为 12.0、46 SM 时自动选择；`NINFER_NVFP4_SM120=0` 在进程启动前关闭。
本地维护测试记录及实际部署状态见工作目录中的 `logs-local/nvfp4-sm120-20261019`。

## 实现范围

- 保留 NVFP4 G16 编码、E4M3 标度、Hadamard 旋转、未量化 Q、BF16 QK、FP16 PV、FP32 累加和输出旋转。
- Br/Bc 仍为 32/32，共享内存仍为 61,312 bytes/CTA；8 warp 替代 16 warp，提高寄存器上限，避免已测 SM120 模板的 local-memory spill。
- K 用成对 FP16 乘法展开，再经过原 BF16 舍入边界。所有合法非负有限 E4M3 标度与 E2M1 码的乘积都能由 FP16 精确表示。
- 按既有检索掩码跳过完全屏蔽的 64-token 页，不分配额外全局 GPU workspace，不缩检索预算或上下文。保留有效页的原始顺序。
- 跳过全屏蔽 tile 省去原来的零贡献 softmax 更新，因此稀疏掩码输出可能有浮点尾差；必须对独立 oracle 验证，不能承诺逐位相同。

此实现仍使用 BF16/FP16 Tensor Core attention；没有将 Q 再量化成 FP4，也没有声称采用原生 FP4 Tensor Core attention。未改 decode/small-T 内核、MTP、采样、历史索引或问句缓存修复。

## 资格检查

`benchmarks/qualification/nvfp4_prompt_sm120.cu` 是独立程序，只依赖 CUDA 和引擎头文件。用 CUDA 13.0.48 / MSVC 14.44.35207、`compute_120a,sm_120a` 编译，包含 `engine/src`、`engine/include`、CUDA include/cccl，不需要链接引擎静态库。

检查全部 byte code 与合法 scale code 的解码、FP64 解码/注意力/输出逆变换参考、24Q/4KV 与 16Q/2KV、直接/批次/有效列元数据、碎片化页、稀疏与全空掩码、尾块及 CUDA Graph 重放。每个非空形状的独立 oracle 检查首尾 query 行和首尾 Q head；全输出另做兼容内核差异、非有限值及 Graph 重放检查。核函数计时采用交错顺序及 CUDA events；它不能替代真实模型 API 性能与召回测量。

真实模型配对保持权重、xhigh、采样、256K 上下文、39168 Device KV、7168 MiB Host KV、sink/recent/retrieve、MTP3 和 chunk128 相同。本轮主配对使用同一源码基线和工具链的两个 exe，期间有纯排版重编，分别记录哈希；不能称为同一二进制。另用最终 exe 的启动开关检查解码。128K/200K 的首次读取与缓存重复分别报告，不能用缓存命中数字冒充首次读取提速。

## 本机整模型记录

这轮最初在独立本地分支验证；最终含完整 Host 压力修复的引擎现随 v0.1.3 发布，下载清单和来源记录固定其真实哈希。旧失败和中间二进制记录保留作历史证据，不作为当前发布引擎。新测试使用维护者的 Huihui Swift-1.5 GSQ-RCO IQ3_XXS + MTP 变体；与 v0.1.2 的模型测试不能直接比较为 KV 质量收益。

| 冷缓存输入 | 兼容路径 prompt | 候选路径 prompt | 耗时减少 | 两版本召回 |
|---|---:|---:|---:|---|
| 131079 tokens | 535.172 s | 434.235 s | 18.86% | 10/10 |
| 204854 tokens | 1204.689 s | 883.475 s | 26.66% | 10/10 |

暖请求分别命中 131074、204849 tokens，仅新算 5 tokens；两路径均 10/10。长上下文主配对中，候选部分生成样本的 MTP 接受率和 decode 低于兼容路径，因此不能把预填充收益解释为稳定的生成提速。

候选在完成这四次召回后接 200K 长输出，于第 375 个完整编号行后因 `Device KV page pool exhausted` 返回错误，未完成 512 行；后续工具与召回没有执行。此错误不是 EOS。

另用同一最终 exe、从新进程分别关/开优化，运行完全相同的请求（206552 输入 tokens，cache=0），两边都一次完成512行、六工具及18/18召回。prompt从683.215s降到359.219s，耗时减少47.42%；八次完整任务请求的墙钟之和从852.405s降到529.511s，减少37.88%。长输出decode为65.33/66.84tok/s，但思考长度不同，不将此小差值视为固定解码开销变化。

首次失败的候选思考与新进程成功时相同，内容是成功输出的逐字前缀。上述新进程成功不能覆盖累计缓存后的失败；后续单独定位出Host重复副本与Host-only闲置缓存未参与LRU回收这两层原因。最早找到的原版NVFP4同类失败为2026-10-16 11:15:46.208，早于SM120优化。完整修复v2通过相同累计序列：四次冷暖召回均10/10、512行一次完成、六工具正确、最终18/18，无页池错误；已替换本机原启动路径并保留旧exe备份。原失败记录保留，且v2为重新编译的二进制。详见[Host压力修复及边界](KV_HOST_PRESSURE.md)、[累计证据](../benchmarks/evidence/nvfp4-sm120/host-pressure.json)；此前数值与解码对照见[原实测证据及当前部署状态](../benchmarks/evidence/nvfp4-sm120/verification.json)。

另以最终同一exe按关/开/开/关顺序测试两个固定seed，共8次请求，短前缀4615tokens被完整保留，每次3072-token生成预算，生产xhigh/采样/MTP3不变。相同seed的含思考输出哈希、token数及MTP接受数全部一致；关闭加权decode为78.264tok/s，开启78.116tok/s（-0.19%）。该控制没有显示明显的直接解码开销退步，但不证明200K任意轨迹速度相同。输出刻意限长用于计时，不计入完整性验收。

这些是一轮固定 seed 的合成测试。保留失败，不将独立内核通过等同于混合长任务稳定，也没有得出 NVFP4 比 rk4v4 质量更高的结论。

本分支仍为本机增量构建，复用原静态库；不声称完成干净全量构建或所有上游测试。其他显卡及满 256K 任务需独立验证。
